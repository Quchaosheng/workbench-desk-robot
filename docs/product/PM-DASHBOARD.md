**每个 schema 只问四个问题**(不问别的,防止会开成技术辩论):

1. 这个字段缺失时,下游是拒绝、降级、还是补默认值?
2. 谁有权写它?(多个写入方 = 冲突源)
3. 它的时间基准是什么?(monotonic / wall clock / 无)
4. 它能不能被 Oracle 污染?(评测字段必须和运行字段物理分开)

第 4 个问题最容易被忽略,但它决定评测结果可不可信。`oracle_id` 这类字段只进 evaluation 模块,不进 reconstruction。

## 三、三个止损决策点

到日子就拍,**不要"再试一周看看"**。

| 日期 | 触发条件 | 你要拍什么 | 影响 |
|---|---|---|---|
| **08/05 晚** | mock 互通没做到 | W1 门推迟到 08/12 | 后面三周各推 2 天,W4 压缩 |

第三条是最重要的止损点。理由:LLM 层最可能吃掉两周调试时间,而它**不是这个系统价值的必要部分**。价值在"验证 + 零误判完成",不在"能听懂人话"。

一个能稳定跑、零误判完成、证据链完整的确定性系统,比一个 LLM 时好时坏的系统更能说明问题。

## 六、W3 冻结前的代码抽查(你亲自做)

08/21 功能冻结前,**每个 owner 随机抽 2 个文件,现场讲三件事**:

1. 这个文件为什么这样写
2. 当时的替代方案是什么
3. 为什么放弃那个方案

答不出来的代码不算完成,即使它能跑。

这条同时进了发布硬门槛。原因:团队用 AI 辅助,最大的风险不是代码质量,是**没人能解释代码**。抽查是唯一能防住这件事的机制。

## 七、发布硬门槛(任一失败不发 v0.1.0)

- False Completion 不为 0
- 出现碰撞、限位穿透或 Agent 越权控制
- 固定脚本需要云 API 才能运行
- 12 个场景、seed 或故障注入规则没有版本化
- 关键事件不完整或任务无法回放
- 36 次实验没有原始数据
- README 未说明限制和失败案例
- 外部人员无法按文档启动
- 任一模块 owner 无法通过代码抽查
- 仓库内存在 AI 工具默认身份的提交或未清理的 AI 工作目录

最后两条是 v2.0 新增的,针对 AI 辅助开发。

## 九、砍范围的优先顺序

到了必须砍的时候,按这个顺序砍。**从上往下砍,不要跳。**

| 顺序 | 砍什么 | 保住什么 |
|---|---|---|
| 1 | 情绪表达动画细节(保留四状态可触发) | 四状态理解率指标 |
| 2 | Dashboard 回放页面的视觉打磨 | 回放功能本身 |
| 3 | "目标移动"场景类别(12→9) | A/B/C 三版本消融 |
| 4 | 自然语言层(LLM→TaskGraph) | 确定性链路 + 36 次评测 |
| 5 | 本地模型 Runner | 无 API Key 可运行的固定脚本 |

**永远不砍的四样**:False Completion = 0、碰撞/越权 = 0、A/B/C 消融、外部人员复现。

这四样是项目的科学价值。砍了它们,月底交付的就只是一个 demo,而不是一个能被验证的系统。
