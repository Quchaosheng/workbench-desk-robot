## 1. 月底要做成什么

在普通电脑上运行一条命令,启动固定桌面单臂仿真机器人。用户输入:

> 把红色模块放进托盘。

必须展示的闭环不变:

```text
摄像头识别红色模块和托盘
  -> WorldState 记录物体、位置、置信度和证据
  -> Agent 将语言转换为受约束 TaskGraph
  -> 机械臂抓取并放置
  -> Verifier 判断模块是否真的在托盘内
  -> 失败时重新观察、重试或请求确认
  -> 屏幕/姿态表达 thinking、uncertain、pleased
  -> Dashboard 回放任务、动作、错误和结果
```

正式演示必须出现一次故障。

### 本月不做(与 v1.0 相同,新增两条)

- 不做移动底盘 P0;不做双活动臂;不训练视觉或大模型;
- 不做真实机械、电机、电源和 PCB;不做复杂 BCI;
- 不让大模型控制关节、速度、急停或任务完成判定;
- 不做第二套仿真器、第二套数据库或第二个运行时 Agent;
- **新增:不做路径阻挡场景**(需要动态障碍物世界,W3 没时间);
- **新增:不追求 30 个场景**,12 个冻结场景足够支撑 A/B/C 结论。

## 3. AI 使用策略

团队使用 AI 辅助开发。以下划分决定成败——**把 AI 用在它强的地方,把人留给它弱的地方。**

### 3.1 高杠杆:激进委托给 AI

| 工作 | 归属 | 备注 |
|---|---|---|
| 所有 schema/协议定义的代码化 | 全员 | 人先在纸上冻结字段语义,AI 生成代码与校验器 |
| FastAPI + SQLite + 迁移 + Replay API | #5 | 标准 CRUD,AI 一次成型 |
| 事件库读写与状态重建 | #5 | |
| **每个接口的 mock 实现** | 全员 | 这是并行开发的关键,见 3.3 |
| Virtual MCU 状态机与协议编解码 | #7 | 状态机代码 AI 很擅长 |
| Dashboard UI 与时间线页面 | #3 | 前端是 AI 最强的领域 |
| 单元测试脚手架与故障用例 | 全员 | 注意 3.4 的计数陷阱 |
| README、接口文档、发布说明 | 全员 | |
| scenario manifest schema 与 validator | #4 | |
| CI 配置与容器构建 | #6 | |

### 3.2 低杠杆:人必须自己驱动

| 工作 | 为什么 AI 帮不上 |
|---|---|
| **Gazebo 物理参数**(摩擦、质量、夹爪接触、solver 迭代) | 只能靠跑出来看,没有正确答案可生成。这是本月最大的技术风险 |
| **MoveIt planning 配置调优** | 同上,经验性 |
| **7 模块集成调试** | bug 在运行时才出现,不在代码里 |
| **启动时间优化** | 要测量才知道瓶颈在哪 |
| **决定不变量是什么** | 这是设计判断,不是实现 |
| **验收口径与指标定义** | PO 的职责,不可委托 |

**给 #8 运动控制的特别提醒**:抓取调参是本月唯一无法用 AI 加速的关键路径。W1 就要开始跑,不要等 W2。

### 3.3 契约优先 + mock:8 人并行的前提

**Day 1-2 必须完成的事**:冻结全部接口 schema,然后每个 owner 用 AI 生成自己模块的 mock。

```
Observation          (#4 定义) -> #5 消费
WorldState / Event   (#5 定义) -> #2 #3 消费
TaskGraph            (#2 定义) -> #8 消费
SemanticAction       (#2 定义) -> #8 消费
ActionResult         (#8 定义) -> #5 消费
VerificationResult   (#5 定义) -> #2 #3 消费
MCU Protocol         (#7 定义) -> #8 消费
EmotionIntent        (#3 定义) -> #3 自用
Scenario Manifest    (#4 定义) -> #5 #6 消费
```

**Day 3 起,每个人对着别人的 mock 开发,不等真实实现。** 这样集成不是月底的大爆炸,而是逐步用真实实现替换 mock。

冻结后改 schema 需要 PO 批准,并同步通知所有下游消费者。

### 3.4 AI 辅助的三个陷阱(必须避开)

**陷阱一:测试数量虚高**

AI 会生成大量 lint/风格测试,把总数撑到很大。**验收只看行为测试数**,风格检查单独计数。

```
✅ 报告方式:47 个行为测试 + 130 个 lint 检查
❌ 报告方式:177 个测试全部通过
```

**陷阱二:没人能解释代码为什么这么写**

规则:**每个模块 owner 必须能对自己模块里任意一个文件回答"为什么这样写、当时的替代方案是什么、为什么放弃"。** 答不出来的代码不算完成,即使它能跑。

W3 冻结前 PO 抽查:每个 owner 随机抽 2 个文件,现场讲。

**陷阱三:文档比代码多**

AI 生成文档很快,容易出现 5000 行文档配 3000 行代码。**docs 与 code 的行数比不超过 1:3**,超了就是在写没人读的东西。

### 3.5 提交纪律

由于团队使用 AI 辅助,公开仓库会留下痕迹。提前定规矩,不要月底才处理:

```bash
# 每个人在开始前设置
git config user.name  "<真实姓名>"
git config user.email "<统一域名邮箱>"
```

- 不使用 AI 工具的默认身份提交(如 `Codex <codex@local>`)
- 不把 AI 工具的 plan/spec 工作目录提交进仓库(加进 `.gitignore` 且**在第一次提交前**加)
- README 里写清开发方式,不隐瞒也不强调:

```markdown
## Development
This project was built with AI-assisted development. Interface contracts,
invariants, verification strategy and all merge decisions are owned by the
listed module owners. Ask any owner to walk through any file in their module.
```

### 正式实验

| 版本 | 定义 |
|---|---|
| A | 固定脚本 + 普通状态机 |
| B | Agent,关闭 WorldState 验证和重新观察 |
| C | 完整系统:Agent + WorldState + 验证 + 恢复 + 表达 |

**12 个冻结场景(相同 seed)**:正常 3、遮挡/低置信度 3、目标移动 3、抓取失败 3。

每个版本跑相同 12 个场景,共 **36 次**。必须报告成功率、恢复率、误判完成、安全违规、人工介入、任务时间、P50/P95 和失败样例。

**流程不变**:Agent C 在运行前冻结 manifest、seed、超时和故障类型;运行后审核感知与 Agent 结果;世界模型工程师重算状态与指标;PO 最后批准。

36 次按每次约 5 分钟(任务 + reset + 日志)估算约 3 小时,W4 有时间跑两轮。

## 7. 发布硬门槛

以下任一失败,不发布正式 `v0.1.0`:

- False Completion 不为 0;
- 出现碰撞、限位穿透或 Agent 越权控制;
- 固定脚本需要云 API 才能运行;
- 12 个场景、seed 或故障注入规则没有版本化;
- 关键事件不完整或任务无法回放;
- 36 次实验没有原始数据;
- README 未说明限制和失败案例;
- 外部人员无法按文档启动;
- **新增**:任一模块 owner 无法对自己模块的抽查文件解释设计理由;
- **新增**:仓库内存在 AI 工具默认身份的提交或未清理的 AI 工作目录。

## 8. PO 每天盯八件事

1. 今天是否有端到端运行结果,而不只是模块代码;

6. 固定脚本是否仍能在断网条件下运行;

8. **抓取成功率今天是多少**(唯一无法用 AI 加速的关键路径,每天要有数)。
